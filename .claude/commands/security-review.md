Выступи в роли security-инженера. Проведи аудит безопасности этого проекта.
Это статический сайт (чистый HTML/CSS/JS, без сборки, без сервера и базы
данных, хостинг — GitHub Pages), поэтому проверяй только то, что реально
применимо к такому стеку — не предлагай RLS, сессии или SQL-защиту, их
здесь нет.

Проверь и исправь:

1. **Секреты в клиентском коде.** Просканируй весь проект (включая
   `.git`-историю последних коммитов) на API-ключи, токены, пароли.
   Публичные ключи форм (например `access_key` от web3forms) — это по
   дизайну не секрет, не считать уязвимостью. Флагать только то, что даёт
   доступ к чужой системе (сервисные ключи, приватные токены, пароли).

2. **Формы.** Для каждой `<form>`: куда уходят данные (action), есть ли
   honeypot/спам-защита, ограничен ли `access_key` формы доменом отправки
   в настройках сервиса форм (если такая опция есть — не проверяется из
   кода, отметь как «проверить в дашборде сервиса»).

3. **Сторонние скрипты.** Каждый `<script src="https://...">`: есть ли
   `integrity` (SRI) и `crossorigin`. Скрипты без SRI с CDN — цепочка
   поставки под риском (если CDN или конкретная версия пакета скомпрометированы,
   код выполнится на сайте без предупреждения). Особо проверь любую
   загрузку библиотек уровня React/Babel в браузере в продакшене — это и
   риск, и лишний вес страницы.

4. **Content-Security-Policy.** Есть ли `<meta http-equiv="Content-Security-Policy">`
   на каждой HTML-странице сайта (не только на index). Проверь директивы:
   `frame-ancestors` (защита от clickjacking — не путать с `frame-src`,
   это разные вещи), `script-src` без `'unsafe-inline'` если реально
   возможно, `connect-src`/`form-action` ограничены только нужными доменами
   (не `*`).

5. **HTTPS и редиректы.** GitHub Pages с кастомным доменом: убедись что в
   настройках репозитория включён «Enforce HTTPS». Прямо из кода это не
   проверяется — отметь как ручную проверку в GitHub Settings → Pages.

6. **robots.txt / sitemap.xml.** Не открывают ли служебные пути, черновики,
   недоделанные разделы, которые не должны индексироваться.

7. **PII в статике.** Нет ли в HTML/JS захардкоженных email/телефонов в
   виде, который легко скрейпить ботам (mailto: без обфускации — это
   осознанный компромисс, не баг, просто отметь).

Формат отчёта для каждой находки:
Уровень: КРИТИЧНО / ВАЖНО / РЕКОМЕНДАЦИЯ
Файл: путь/к/файлу:строка
Проблема: что не так
Риск: что может случиться
Фикс: конкретное исправление с кодом (или «ручная проверка в панели X», если
это не решается кодом)

Не придумывай проблем ради количества — если аспект неприменим к
статическому сайту, явно напиши «неприменимо» и почему.
